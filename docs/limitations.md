# Limitations

This document lists the known limitations of the prototype. Readers and evaluators should be aware of these before drawing conclusions about production readiness.

## Data

1. **Synthetic data only.** All data is generated by `src/backend/data/synthetic/generator.py` with `seed=42`. It does not represent any real fabrication facility, product family, or process technology.

2. **Simplified process flow.** A real fab lot goes through 200–500 process steps. This prototype models a single step per wafer (one run per wafer) to keep the dataset tractable. The analytical patterns are valid but the data volume per lot is not representative.

3. **Approximated derived features.** Pre-run features `chamber_yield_30d`, `days_since_last_pm`, and `chamber_ooc_rate_30d` are filled with constant values in the prototype. In production these would be rolling-window aggregates computed from the full process history.

4. **No real-time data ingestion.** The data is static (seeded once). There is no streaming, OPC, or equipment interface. Real integration would require connectors to fab MES, equipment datastores, and SPC systems.

## Analytics

5. **Heuristic thresholds not validated.** All excursion thresholds (MAD σ cutoffs, z-score levels, pattern classification boundaries) are set for demonstration on synthetic data. They have not been validated against real process data or characterised for type I/II error rates.

6. **Defect pattern classification is demonstrative.** The spatial pattern classifier uses simple geometric heuristics. It is not a production-certified defect classification method and has not been benchmarked against human expert classifications.

7. **Root-cause fusion weights are fixed.** The 7 signal weights are hard-coded constants. In a real system they would be calibrated against known-cause historical excursions.

8. **No causal inference.** The system produces ranked evidence-based candidates, not causal graphs. Correlation ≠ causation. All outputs require engineering review.

9. **Similar-lot matching is shallow.** The cosine similarity feature vector is 4 dimensions. A production similar-lot system would include more features and potentially account for process-step sequence similarity.

## Pre-Run Model

10. **No production training pipeline.** The GBM model is retrained from scratch on every API request (~5 seconds). A production system would run scheduled retraining and cache the model.

11. **No hyperparameter optimisation.** Default scikit-learn `GradientBoostingClassifier` parameters are used.

12. **Class imbalance not addressed.** The synthetic dataset produces roughly 15–25% positive labels. No class weighting, oversampling, or cost-sensitive learning is applied.

## Infrastructure

13. **PostgreSQL required for full operation.** The test suite uses SQLite in-memory. Running the application live requires PostgreSQL 15 (via Docker Compose). The ingestion SQL uses only standard SQL features so any PostgreSQL-compatible database will work.

14. **No authentication or authorisation.** The API has no auth layer. In production, all endpoints would require authentication and role-based access control. The engineer review endpoint in particular must only be accessible to authorised personnel.

15. **In-memory action store.** The actions router uses an in-memory dictionary for demo purposes. All reviews are lost on server restart. In production, reviews would be persisted to the `action_reviews` database table.

16. **No audit log persistence.** Evidence records and root-cause results are computed on demand and not persisted to the database (the `excursions`, `root_cause_candidates`, and `pre_run_assessments` tables exist but are not populated by the API). In production, results would be persisted to enable audit trail.

## Frontend

17. **No authentication UI.** The engineer reviewer field is a free-text input. In production this would be tied to an authenticated session.

18. **No pagination beyond lot list.** The evidence, root-cause, and patterns screens show up to a fixed cap of results without pagination.

19. **30-second polling is approximate.** The monitor screen refreshes every 30 seconds via `setInterval`. In production, WebSocket or SSE would be preferred.

## Scope Exclusions (by design)

These are explicitly out of scope for this prototype per the challenge brief:

- Kafka, Spark, Kubernetes, cloud infrastructure
- Vector databases or LLM integration
- Real-time equipment interface (OPC-UA, SECS/GEM)
- Multi-tenant or multi-fab deployment
- Recipe management or lot disposition systems
- Statistical process control (SPC) chart rendering
